## Потеря и повтор задач

- [x] **Ack в `ensure` теряет задачу при сбое Redis.** `processor.rb:68-75`:
  `acknowledge(work)` выполняется и тогда, когда `execute` упал не из-за
  самой задачи, а из-за Redis — на `register_in_workers` (hset), на
  `incr STATS_FAILED`, на `zadd RETRY/DEAD` в `route_failure` или в
  `bury_unparseable`. Задача удаляется из in-progress, не попав ни в retry,
  ни в dead; её unique/periodic-блокировка висит до TTL. Сценарий: на одном
  соединении пула `ReadTimeout`, `zadd RETRY` падает, ack на другом
  соединении проходит. Делать ack только при нормальном завершении
  `execute`, при исключении — оставлять задачу в in-progress или `give_back`.
- [x] **Ложное признание процесса мёртвым → двойное выполнение.**
  `reliable_fetch.rb#recover_orphans` (стр. 88) считает процесс мёртвым по
  одному отсутствию `cogworker:process:<identity>` (TTL 60 с). Живой
  процесс, который 60 с не смог сделать beat (сбой/failover Redis, GVL
  удерживает C-расширение, ключ удалён вручную), теряет свои задачи — их
  возвращает в очередь другой процесс, и они выполняются дважды. Отдельно:
  если Redis недоступен на старте, первый синхронный beat
  (`heartbeat.rb:29`, `beat_safely`) только логирует ошибку, а Manager всё
  равно начинает забирать задачи без ключа присутствия.
  *Старт исправлен:* `Heartbeat#start!` повторяет первый beat до успеха,
  Manager до этого не запускается (`TERM` при этом обрабатывается).
  *Порог:* каждый beat пишет время (по часам Redis) в `cogworker:last_beat`;
  процесс мёртв, только если нет ключа присутствия **и** последний beat
  старше `config.orphan_threshold` (по умолчанию 300 с).
  `RunningLock.active_ttl` считается от этого порога.
- [x] **`until_executed` не соблюдается после восстановления сироты.**
  Periodic-блокировка мёртвого процесса живёт `RunningLock::ACTIVE_TTL`
  (60 с), а сироты поднимаются не раньше TTL heartbeat (60 с) плюс до
  `ORPHAN_CHECK_INTERVAL` (60 с). Восстановленная задача со старым jid
  стартует без блокировки (`shorten_lock`/`release` — no-op, владелец уже
  другой), а ticker тем временем мог поставить новый слот → два прогона
  одной записи параллельно. Переставлять блокировку на восстановленную
  задачу при requeue или держать её, пока задача в in-progress.
- [x] **Слот cron теряется при сбое push.** `periodic/ticker.rb#enqueue`:
  если `Client.push` упал после успешного claim, блокировка снимается, но
  `periodic:last_slot` уже записан в `claim.lua`, поэтому следующий тик
  получит 0. Комментарий на `ticker.rb:61` («the next tick retries it»)
  неверен. Откатывать `last_slot` вместе с блокировкой.
- [x] **`claim_and_requeue` не атомарен.** `job_util.rb:77-84`: `zrem` и
  `requeue` (multi + lpush) — отдельные команды; падение между ними теряет
  задачу из retry/schedule. Перенести в один Lua-скрипт.

## Надёжный fetch: нагрузка и совместимость

- [x] **Опрос вместо блокирующего ожидания.** `reliable_fetch.rb:112-115`:
  при пустых очередях каждый поток шлёт полный `EVAL` (без `EVALSHA`) раз в
  `EMPTY_POLL_INTERVAL` = 0.25 с — при concurrency 25 это ~100 EVAL/с на
  простаивающий процесс, задержка подхвата до 0.25 с. Как минимум
  `EVALSHA`; лучше `BLMOVE` для одной очереди или адаптивный backoff.
- [x] **`supported?` при недоступном Redis возвращает `true`.**
  `reliable_fetch.rb:68`: если Redis не отвечает на старте, режим
  `:reliable` выбирается без проверки версии. На Redis < 6.2 после этого
  каждый fetch падает с `ERR unknown command LMOVE` — процесс жив, но ничего
  не делает, только пишет ошибку раз в секунду. Повторять проверку при
  первой ошибке `unknown command` или откатываться на `:basic` в рантайме.
  Заодно: `Manager.new` теперь ходит в Redis прямо в конструкторе.
- [x] **`recover_orphans` сканирует весь keyspace.** `SCAN MATCH
  cogworker:inprogress:*` раз в 60 с в каждом процессе — O(всех ключей БД).
  *Сделано:* обход множества `cogworker:inprogress_identities` (каждый
  reliable-процесс регистрируется в нём при beat); keyspace-`SCAN` — один
  раз при старте и только в `fetch: :reliable` (для списков от 0.3.0).
  В `:basic` проверка не отключена совсем намеренно: при смешанном флоте
  или рантайм-откате на `:basic` списки упавших reliable-процессов иначе
  никто не вернёт; при пустом множестве это один `SMEMBERS` раз в 60 с.
- [x] **CI не проверяет откат на `:basic`.** Матрица использует только
  `redis:7`; добавить сервер < 6.2 (например `redis:6.0`).

## Прочее

- [x] **Последние строки лога теряются при выходе процесса.**
  `swarm.rb:72` и `heartbeat.rb:197` завершают процесс через
  `Process.exit!`, который не сбрасывает буферы Ruby IO. Когда stdout —
  pipe (docker, systemd), последние строки (например `done: <Job>`) не
  попадают в лог. Наблюдалось вживую: задача в History `success`, строки
  `done:` нет. `$stdout.sync = true` в `Logging.default_logger` или
  `$stdout.flush`/`$stderr.flush` перед `exit!`.
- [x] **Лишняя cookie `cogworker.session`.** `web.rb:250` всегда
  подключает свою `Rack::Session::Cookie`, даже если приложение поставило
  свою через `Web.use`. Дать отключить встроенную сессию.
- [ ] **Классы обычных задач по-прежнему разрешаются лениво в потоках.**
  `Launcher#resolve_periodic_classes` закрывает только periodic-записи;
  задачи, запускаемые только через `perform_async`, всё так же
  резолвятся в `Processor#build_worker` в рабочем потоке (README советует
  eager load). Можно добавить опцию списка классов/путей для предзагрузки.
