`v0.4.0..v0.4.1` и живой прогон в проекте на Ruby 3.2.9 + redis-rb 4.8.1.
Пути — относительно `lib/cogworker/`.

## Высокий приоритет

- [x] **Одна «битая» identity останавливает Scheduled и cron по всему
  флоту.** `scheduled.rb:83-92`: `recover_orphans` (суммирование по
  identity) и `reconcile` не изолируют ошибки отдельной identity, а
  `@recovered_once`/`@next_orphan_check` выставляются только при успехе, и
  `enqueue_due_jobs` идёт в том же блоке после них. Ticker ждёт
  `recovered_once?`. При постоянной ошибке ни один процесс не переносит
  задачи из retry/schedule в очереди, а periodic-записи не тикают никогда.
  Триггеры: `cogworker:inprogress:<id>` не того типа (`WRONGTYPE`),
  нечисловой `last_beat` (`attempt to perform arithmetic on a nil value` в
  `REQUEUE_SCRIPT`), ACL, запрещающий `TIME` (`reliable_fetch.rb:91`).
  Воспроизводится: `SADD cogworker:inprogress_identities ghost` +
  `SET cogworker:inprogress:ghost x` → `recovered_once=false`, задача
  остаётся в schedule. Изолировать ошибку на уровне одной identity (лог и
  пропуск), `enqueue_due_jobs` вызывать независимо от восстановления, Ticker
  не блокировать навсегда (таймаут ожидания первой проверки).

## Средний приоритет

- [x] **`interrupt` игнорирует `retry: false` / `retry: 0`.**
  `processor.rb:123-133`: задача, у которой упала запись о неудаче, уходит в
  retry через `INTERRUPT_DELAY` и выполняется ещё до `MAX_INTERRUPTS` (3) раз
  — даже если повторы ей запрещены. Для задач с побочными эффектами
  (платежи) это нарушает явный контракт `retry: false`. Для таких задач —
  сразу в dead.
- [x] **Бесконечный повтор, если у исключения падает `#message`.**
  `processor.rb:238` (лог) и `:290` (`route_failure`) вызывают
  `JobUtil.error_message(error)` вне защиты; исключение из `#message`
  пробрасывается из `execute` → `give_back` → повтор примерно раз в секунду,
  в dead не попадает. Оборачивать получение сообщения
  (`rescue Exception` → `"#<#{error.class}>"`), лог-строку делать
  best-effort.
- [x] **Reconcile перезапускает отработавшие задачи с неудачным ack.**
  `reliable_fetch.rb:198-210`: если LREM (ack) не прошёл за 3 попытки,
  задача остаётся в in-progress без записи в `cogworker:workers:<id>`, и
  через два наблюдения reconcile возвращает её в очередь — второй прогон, а
  если неудача уже записана в retry, то задача и в retry, и в очереди.
  Противоречит обещанию «never re-run» в README. Перед requeue проверять
  маркер завершения (например, `settled:<jid>` с коротким TTL).
- [x] **Reconcile может задублировать работающую задачу.** Если hash
  `cogworker:workers:<id>` потерян (failover с потерей последних записей), а
  задача идёт дольше 60–120 с, reconcile вернёт её в очередь, и она
  выполнится параллельно с текущим прогоном. Сверять с локальным
  in-memory списком выполняемых jid процесса, а не только с Redis.

## Низкий приоритет

# Проверка рабочего дерева поверх 0.4.1 (2026-10-02)

Ревью незакоммиченного диффа (`git diff fddb310`) и живые сценарии на swarm
проекта (Ruby 3.2.9 + redis-rb 4.8.1, Redis 8.4). Пути — относительно
`lib/cogworker/`.

## Высокий приоритет

- [x] **Повтор уже выполненной задачи при неожиданном исключении после
  `perform`.** `processor.rb:91`: `disposition = :give_back` по умолчанию,
  поэтому любое исключение из `execute` *после* `run_job` (баг в
  `finish_failure`/`finish_success`, логгер, middleware после perform)
  возвращает задачу в очередь сразу — без счётчика, бесконечно. Вживую:
  исключение в начале `route_failure` → 21 прогон за 3 с у задачи с
  `retry: false`. Реальный сбой Redis этот путь не задевает (`route_failure`
  ловит его сам и уходит в `interrupt`), но для задач с побочными эффектами
  риск остаётся. Как только `perform` начался, дефолт должен быть
  `interrupt` (или dead для `retry: false`), а не `give_back`.
- [x] **Потеря задачи в Lua при ключах не того типа.** Скрипты делают `LPOP`,
  а следующая запись падает — Redis не откатывает уже выполненные команды:
  - `REQUEUE_SCRIPT` (`reliable_fetch.rb:87`): `cogworker:repeat_orphans`
    не списка (`WRONGTYPE`) или нечисловой `cogworker:orphanings:<jid>`
    (`ERR not an integer`) — задачи нет ни в in-progress, ни в очереди;
  - `CLAIM_AND_REQUEUE_SCRIPT` (`job_util.rb:78`): очередь не того типа —
    запись из retry/schedule потеряна.
  Проверять `TYPE` целевых ключей до `LPOP`/`ZREM` или переносить без
  удаления источника до успешной записи.

## Средний приоритет

- [x] **Изоляция ошибок закрыта не везде.**
  - `IN_PROGRESS_IDENTITIES` (`reliable_fetch.rb:301`, `SMEMBERS`) или
    `REPEAT_ORPHANS` (`reliable_fetch.rb:242`) не того типа роняют всё
    восстановление: `@recovered_once`/`@next_orphan_check` не выставляются,
    и каждые 5 с на каждом процессе идёт полный `SCAN` keyspace.
  - `enqueue_due_jobs` (`scheduled.rb:116-122`) не изолирует множества и
    записи: `cogworker:schedule` не того типа — `cogworker:retry` не
    переносится вовсе; одна запись с падающим `graduate` обрывает весь опрос.
  - `Ticker#tick` (`periodic/ticker.rb:102-113`) не изолирует записи:
    исключение у одной periodic-записи пропускает все последующие на каждом
    тике; `PERIODIC_DISABLED`/`PERIODIC_SCHEDULE` не того типа роняют все
    тики.
  - `cogworker:workers:<id>` не того типа: `hset` в `register_in_workers`
    падает до запуска → `give_back` → задача крутится, не выполняясь.
- [x] **`retry: false` + детерминированно падающая запись в dead → повтор
  каждые ~2 мин.** `route_failure` и `interrupt` пишут в один и тот же
  `cogworker:dead`; если он не того типа, оба падают, задача остаётся в
  in-progress, и reconcile после двух наблюдений возвращает её в очередь —
  бесконечно. Нужен счётчик и для этого пути.
- [x] **Повтор после неудачного ack — незакрытые ветки.** Список неудачных
  ack хранится только в памяти (`processor.rb:168`, `manager.rb:155-164`):
  - процесс упал (OOM/SIGKILL) после неудачного ack → восстановление сироты
    перезапускает выполненную задачу (если её неудача уже в retry — она и в
    retry, и в очереди);
  - `finish_failed_acks` поймал ошибку, а следующий `requeue_in_progress`
    при остановке прошёл (`manager.rb:145`) → повтор. Сбой
    `finish_failed_acks` должен отменять requeue или исключать эти payload;
  - задача отработала, но не прошли ни запись неудачи, ни `interrupt` →
    уходит в strays и выполняется заново.
  README («never re-run because of a Redis error after it ran») обещает
  больше; нужен маркер завершения в Redis или уточнение в README.
  *Сделано:* неудачный ack и незаписанная неудача хранятся вместе как
  «отложенное завершение»; reconcile и `stop!` их довершают, не перезапуская;
  при `stop!` недодавленные ack снимаются атомарно (`except:`). Падение
  процесса до завершения — неустранимый повтор (маркер в Redis не записать,
  Redis и есть причина сбоя): README уточнён.
- [x] **README про `interrupt` устарел.** Пишет «goes to Retry … to Dead
  after 3»; не сказано, что `retry: false`/`0` идут в Dead сразу. Строка
  лога «interruption n/3» при уходе в dead вводит в заблуждение.

## Низкий приоритет

- [x] **Счётчик сирот задевает соседей.** `cogworker:orphanings:<jid>`
  растёт у всех задач, выполнявшихся в упавшем процессе, а не только у
  виновницы; `MAX_ORPHANINGS` = 3 (`reliable_fetch.rb:31`) не
  настраивается; при переносе в dead не снимаются unique/RunningLock и не
  растёт `stats:failed`; ключи живут `ORPHANINGS_TTL` (7 дней) и не
  удаляются при успехе.
- [x] **Ожидающие откаты слота cron только в памяти.** `@pending_rollbacks`
  (`periodic/ticker.rb:53`) теряются при рестарте процесса; это описано в
  комментарии кода, но не в README.
- [x] **Список выполняемых задач в памяти по сырому payload.** Два
  одновременных прогона с одинаковым raw (дубль в очереди) делят одну
  запись — первый завершившийся снимает защиту второго от reconcile.
- [x] **`Heartbeat#touch_running_periodic_locks` читает
  `cogworker:workers` из Redis** — если hash потерян при failover,
  `RunningLock` истечёт посреди долгой задачи. Брать список из памяти, как
  reconcile.
- [x] **Ключ счётчика собирается внутри Lua**, а не передаётся в `KEYS` —
  несовместимо с Redis Cluster (как и существующие lock-ключи).
  *Задокументировано:* README — Redis Cluster не поддерживается.

*Системно:* добавлен `KeyGuard` — при старте и раз в минуту ключи гема не
того типа переименовываются в `cogworker:quarantine:<key>:<time>` (30 дней)
с ошибкой в логе; система продолжает работу со свежим ключом.

## Подтверждено живыми сценариями (без замечаний)

`retry: false` → dead с одного прогона; не-UTF-8 сообщение и падающий
`#message`; отказ ZADD в retry/dead → `interrupt` (dead для `retry: false`,
retry через 30 с для `retry: 2`); неудачный ack на 6 с — один прогон,
reconcile дожимает ack; «битая» identity (`WRONGTYPE`, нечисловой
`last_beat`) — schedule и cron продолжают работать; cron 90 с при слоте
1 мин с `until_executed` — прогоны не пересекаются; SIGKILL во время cron —
восстановление через ~70 с без параллельного слота; задача, убивающая свой
процесс, — в dead после 3 восстановлений; потеря `cogworker:workers:<id>`
во время 170-с задачи — без дубля; TERM при задаче дольше таймаута — возврат
в очередь (at-least-once, как задокументировано).

# Повторная проверка рабочего дерева (2026-10-02, после правок по второму разделу)

Ревью диффа против `fddb310` и живые сценарии на swarm проекта (Ruby 3.2.9
+ redis-rb 4.8.1). Сценарии C1–C9 — порча ключей Redis и сбои при работающем
swarm. Пути — относительно `lib/cogworker/`.

## Высокий приоритет

- [x] **Ключ не того типа роняет весь heartbeat → процессы не стартуют.**
  `heartbeat.rb:129-130`: `sadd?(IN_PROGRESS_IDENTITIES)` и
  `hset(LAST_BEAT)` стоят в одном блоке `beat` без изоляции. Если
  `cogworker:inprogress_identities` (или `cogworker:last_beat`) не того типа,
  beat падает целиком: `Heartbeat#start!` ждёт первого успешного beat
  бесконечно, и новый процесс не стартует — на всём флоте (вживую: дочерний
  процесс после SIGKILL не поднялся, `Heartbeat failed: WRONGTYPE` раз в
  секунду; поднялся сразу после починки ключа). У работающих процессов
  перестаёт продлеваться `RunningLock` долгой cron-задачи → возможен
  параллельный слот. Ключ присутствия и `last_beat`/реестр писать отдельно,
  best-effort для второстепенных записей.
- [x] **`periodic:disabled` не того типа останавливает весь cron.**
  `periodic/ticker.rb:171-172`: `disabled?` (`SISMEMBER`) падает у каждой
  записи, и не тикает ни одна (вживую: 0 тиков за 75 с, после починки —
  сразу пошли). Ошибку `disabled?` считать «не отключена» (или кэшировать
  последнее известное состояние) и логировать.

## Средний приоритет

- [x] **Восстановление сирот блокируется на головной задаче.**
  `reliable_fetch.rb:87` (`REQUEUE_SCRIPT`): если у первой задачи списка
  in-progress мёртвого процесса очередь назначения не того типа, скрипт
  падает на ней каждый раз, и все задачи за ней не восстанавливаются никогда
  (раньше терялась одна задача, теперь застревают все). То же при
  shutdown-requeue своего списка. `redis.pcall` на запись и пропуск/ротация
  такой задачи (или перенос в dead).
- [x] **`retry: false` + детерминированно падающая запись в dead → повтор на
  каждом деплое.** Пока процесс жив, задача держится как отложенное
  завершение (вживую OK), но `Manager#requeue_unfinished`
  (`manager.rb:158`) возвращает её в очередь при каждой остановке — после
  рестарта она выполняется снова. Для платёжных задач — повтор на каждый
  деплой. Не возвращать в очередь задачи с отложенным завершением типа
  `[set, score, payload]` или считать такие возвраты.
- [x] **Голодание при переносе из retry/schedule.**
  `scheduled.rb:131`: `zrangebyscore … limit: [0, 50]` — если 50 самых
  старых записей стабильно не переносятся (очередь назначения не того типа),
  каждый опрос берёт их же, и всё, что за ними, не переносится никогда.
  Сдвигать окно (offset) или откладывать непереносимые записи (score +
  backoff).

## Низкий приоритет

- [x] **Ожидание первой проверки сирот снова не защищает.**
  `scheduled.rb:114`: `@recovered_once = true` выставляется даже при
  полностью неудачной проверке (`recover_orphans` больше не бросает) — при
  недоступном на старте флота Redis Ticker не ждёт реального восстановления,
  и возвращается окно двух параллельных прогонов `until_executed`.
- [x] **Разовый SCAN не повторяется после сбоя.** `scheduled.rb:110-111`:
  `@scanned = true` выставляется до SCAN; если первый SCAN упал, старые
  in-progress-списки (без записи в реестре) больше не ищутся никогда.
- [x] **Лимит сирот не применяется при битом `repeat_orphans`.** Вживую:
  задача со счётчиком на лимите после SIGKILL при `repeat_orphans` не того
  типа перезапущена, а не отправлена в dead (потери нет, но
  `max_orphanings` обходится).
- [x] **Исключение в `interrupt` до записи → повтор каждые ~2 мин.**
  `processor.rb:132-149`: например `retry: {}` → `max_retries` бросает
  `NoMethodError`; внешний rescue не вызывает `settle_later`, задача
  становится stray и reconcile перезапускает её.
- [x] **Шторм повторов для cron-записи с детерминированно падающим push.**
  Откат и повторный push идут каждый тик (5 с): вживую 27 ошибок за 70 с на
  двух процессах. Нужен backoff для `retry_pending_rollbacks`
  (`periodic/ticker.rb:165`) и повторов push одной записи.
- [x] **Устаревший комментарий** `processor.rb:204` («before the job has
  run (then `process_one`'s default, :give_back …») — дефолт уже не
  `:give_back`.
- [x] **README про откаты cron** (`README` ~306-310) не упоминает, что
  блокировка `until_executed` при неудачном откате висит до TTL.

## Подтверждено живыми сценариями (без замечаний)

Регрессия S1–S5c; исключение в `route_failure` после perform — 1 прогон →
dead; `cogworker:schedule` не того типа — retry переносится; очередь
назначения не того типа — запись остаётся в retry и переносится после
починки; нечисловой `orphanings:<jid>` + SIGKILL — задача восстановлена;
`cogworker:workers:<id>` не того типа — задача выполнена; `cogworker:dead`
не того типа + `retry: false` — без повторов, пока процесс жив, после
починки — в dead; одна cron-запись с падающим push не мешает остальным.

# Проверка рабочего дерева, прогон 3 (2026-10-03, после правок по третьему разделу)

Ревью диффа против `fddb310` и живые сценарии на swarm проекта (Ruby 3.2.9
+ redis-rb 4.8.1). Все живые сценарии прогона прошли (см. ниже). Пути —
относительно `lib/cogworker/`.

## Средний приоритет

- [x] **Backoff тикера срабатывает и на ошибках соединения.**
  `periodic/ticker.rb:116-126`: `rescue StandardError` в `tick` наращивает
  `back_off` (5 → 300 с) для каждой записи, в том числе на

  всех записей доходит до 160–300 с, и после возврата Redis cron стоит ещё
  до 5 минут; при `periodic_catch_up` пропущенные слоты схлопываются в один
  прогон. Тот же backoff у `retry_pending_rollbacks`. На ошибках соединения
  не наращивать backoff (или ограничить его ~5–10 с), наращивать только на
  ошибках самой записи.
- [x] **Окно параллельного прогона `until_executed` после долгого отказа
  Redis на старте.** `scheduled.rb:73-75`: `ready_for_ticker?` отпускает
  Ticker через `READY_TIMEOUT` (120 с), а следующая проверка сирот
  назначается до прогона (+60 с). Если Redis недоступен на старте флота
  дольше 120 с, после его возврата Ticker может тикнуть раньше восстановления
  сирот — окно до 60 с. Плюс: если реестр прочитан, а requeue упал по
  соединению, `recovered_once` всё равно становится true. Отпускать Ticker
  только после успешной проверки (или проверку запускать сразу при
  восстановлении соединения).

## Низкий приоритет

- [x] **`touch_running_periodic_locks` не изолирован по ключам.**
  `heartbeat.rb:164`: один `periodic:running:*` не того типа — beat
  логируется как failed, и блокировки после него не продлеваются (присутствие
  процесса уже записано). Изолировать по каждой блокировке.
  *Не подтвердилось:* изоляция по каждой блокировке уже есть (проверено:
  при `periodic:running:a` не того типа блокировка `b` продлевается, beat
  успешен).
- [x] **Счётчик `orphanings:<jid>` не того типа отключает лимит сирот.**
  Например list: `max_orphanings` не срабатывает никогда (5 сиротств,
  dead=0). KeyGuard такие ключи не проверяет.
- [x] **Запасной путь в dead (битый `repeat_orphans`) неполный.** Задача
  уходит в dead сырым payload без `error_class`/`error_message`, без
  `buried_as_dead` (`reliable_fetch.rb:440`): нет `stats:failed`, не
  снимаются unique-блокировки, счётчик `orphanings` остаётся на 7 дней.
- [x] **Не все пути подтверждения чистят счётчик сирот.** `settle_pending`
  (`reliable_fetch.rb:385`, :ack) и `except:` при shutdown-requeue удаляют
  задачу из in-progress, но не трогают `orphanings:<jid>` — остаток может
  позже ускорить попадание невиновной задачи в dead.
- [x] **`FILE_UNSETTLED_SCRIPT` / `settle_pending` не повторяют побочные
  действия терминального пути** (`reliable_fetch.rb:232,385`): нет
  `stats:failed`, unique-блокировка `until_executed` не снимается (висит до
  TTL), нет `extend_locks_for_retry` (сейчас безопасно: задержка ≤ 90 с при
  active_ttl ~420 с).
- [x] **Повторный карантин того же ключа в ту же секунду затирает копию.**
  `key_guard.rb`: имя `cogworker:quarantine:<key>:<unix-сек>`, RENAME второго
  карантина в ту же секунду перезаписывает первый. Добавить уникальный
  суффикс или `RENAMENX` с повтором.
- [x] **`ROLLBACK_SCRIPT` делает `GET` блокировки без `pcall`.**
  `periodic/ticker.rb` (скрипт отката, `GET KEYS[3]`): выполняется и для
  записей без `until_executed`; если ключ блокировки не того типа, откат
  фактически применён, но считается неудачным и повторяется вечно (с
  backoff).
- [x] **Комментарий противоречит коду.** `scheduled.rb:112-113` («SCAN
  marked done before it's tried») — теперь `@scanned` выставляется после
  успешного SCAN.

## Подтверждено живыми сценариями (без замечаний)

Регрессия S1–S5d; `inprogress_identities` не того типа — процесс стартует,
ключ в карантин; `periodic:disabled` не того типа — ключ в карантин, cron
тикает; push одной cron-записи падает всегда — backoff (6 попыток за 130 с на
2 процесса), остальные записи тикают; голова in-progress мёртвого процесса с
очередью не того типа — задачи за ней восстановлены, голова сохранена;
60 непереносимых записей в retry — обычная запись перенесена; `repeat_orphans`
не того типа + задача на лимите + SIGKILL — ключ в карантин, задача в dead;
`cogworker:dead` не того типа + `retry: false` + TERM — ключ в карантин,
отложенное завершение доведено при остановке, без повтора после рестарта.
